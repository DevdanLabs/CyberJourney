# Executive Summary

Incident Response (IR) is a structured approach used by organizations to detect, analyze, contain, eradicate, recover from, and learn from cybersecurity incidents. Since no organization can completely prevent every attack, having an effective incident response process is essential to minimize damage, reduce downtime, preserve digital evidence, and restore business operations.

In this room, we explored the complete lifecycle of an incident—from understanding the difference between events, alerts, and incidents to learning how security teams prioritize incidents using severity levels. We also studied common types of security incidents, including malware infections, data leaks, insider attacks, security breaches, and denial-of-service attacks.

The room introduced two of the most widely adopted Incident Response frameworks: the **SANS PICERL** model and the **NIST Incident Response Lifecycle**. In addition, we learned how security technologies such as **SIEM**, **Antivirus (AV)**, and **Endpoint Detection and Response (EDR)** support analysts throughout the response process. Finally, we completed a practical lab that simulated a phishing campaign, investigated infected hosts, performed containment actions, and analyzed an endpoint process timeline.

# Understanding Security Incidents

Before learning how to respond to an incident, it is important to understand what actually qualifies as one. Every system continuously generates thousands—or even millions—of events during normal operation. Most of these events are completely legitimate, while only a very small percentage indicate malicious activity.

The Incident Response process begins by distinguishing normal system activity from actual security incidents.

---

# Events, Alerts, and Incidents

One of the most important concepts introduced in this room is the relationship between **events**, **alerts**, and **incidents**.

## Events

An **event** is any activity that occurs on a computer, application, or network device.

Examples include:

- User logins
- File creation
- Process execution
- Network connections
- Registry modifications
- Service startups
- PowerShell execution

Every running process generates events that are recorded by the operating system or security software.

For example:

```text
Explorer.exe
      │
      ▼
Open Folder

Chrome.exe
      │
      ▼
HTTPS Connection

LSASS.exe
      │
      ▼
User Authentication
```

Most events are completely normal and do not represent malicious activity.

---

## Alerts

Since organizations generate millions of events every day, manually reviewing them is impossible.

Security solutions such as SIEM and EDR continuously analyze these events. When suspicious activity is detected, they generate an **alert**.

An alert simply means:

> "Something unusual happened and requires investigation."

Examples include:

- Multiple failed login attempts
- Large outbound data transfers
- PowerShell spawning from Microsoft Word
- Execution of known malware

An alert does **not** automatically mean a system has been compromised.

---

## False Positives vs True Positives

After an alert is generated, security analysts investigate it to determine whether it represents legitimate or malicious activity.

### False Positive

A False Positive occurs when legitimate activity is incorrectly identified as malicious.

Example:

- Large data transfer detected
- Investigation reveals an authorized cloud backup

Result:

```text
Alert
   │
   ▼
False Positive
   │
   ▼
Discard
```

---

### True Positive

A True Positive occurs when the suspicious activity is confirmed to be malicious.

Example:

- Phishing email detected
- User downloaded a malicious attachment
- Malware executed successfully

Result:

```text
Alert
   │
   ▼
True Positive
   │
   ▼
Incident
```

---

## What is an Incident?

A **Security Incident** is a confirmed event that threatens one or more components of the CIA Triad:

- Confidentiality
- Integrity
- Availability

Examples include:

- Malware infections
- Unauthorized access
- Credential theft
- Data exfiltration
- Ransomware attacks
- Denial of Service attacks

Only after an alert has been validated as malicious does it become an incident requiring the Incident Response process.

---

# Incident Severity

Not every incident requires the same level of urgency.

Organizations classify incidents according to their potential business impact.

Typical severity levels include:

| Severity | Description |
|----------|-------------|
| **Low** | Minimal impact with limited risk to business operations. |
| **Medium** | Moderate impact that affects one or more systems but remains contained. |
| **High** | Significant impact requiring immediate attention due to business or security risk. |
| **Critical** | Severe impact affecting critical infrastructure, sensitive data, or business continuity. |

Incident severity determines which incidents analysts should prioritize first.

For example:

```text
Critical
      │
      ▼
High
      │
      ▼
Medium
      │
      ▼
Low
```

It is important to note that severity depends on the organization's business context rather than the attack type itself.

---

# Common Types of Security Incidents

The room introduces several categories of security incidents commonly encountered by Incident Response teams.

## Malware Infection

Malware refers to malicious software designed to compromise systems or steal information.

Examples include:

- Viruses
- Worms
- Trojans
- Ransomware
- Spyware
- Remote Access Trojans (RATs)

Common infection vectors include:

- Phishing attachments
- Malicious downloads
- USB devices
- Software vulnerabilities

---

## Security Breach

A Security Breach occurs when an unauthorized individual gains access to confidential systems or information.

Examples include:

- Compromised administrator accounts
- Unauthorized VPN access
- Unauthorized database access

A breach may occur even if no data has yet been stolen.

---

## Data Leak

A Data Leak occurs when sensitive information becomes exposed to unauthorized parties.

Unlike security breaches, data leaks may result from:

- Human error
- Misconfigured cloud storage
- Accidental disclosure
- Successful cyberattacks

Examples include:

- Publicly accessible databases
- Customer information leaks
- Source code exposure

---

## Insider Attack

An Insider Attack originates from someone who already has authorized access to organizational resources.

Examples include:

- Disgruntled employees
- Contractors
- Administrators
- Third-party vendors

Because insiders already possess legitimate access, these attacks can be particularly difficult to detect.

---

## Denial of Service (DoS)

A Denial of Service attack targets the **Availability** component of the CIA Triad.

The attacker overwhelms a system with excessive requests until legitimate users can no longer access the service.

Example:

```text
Normal Users
      │
      ▼
Web Server

Attacker
      │
Millions of Requests
      ▼
Server Resources Exhausted
      ▼
Service Unavailable
```

When multiple compromised systems participate simultaneously, the attack becomes a **Distributed Denial of Service (DDoS)** attack.

# Key Takeaways

- Every system continuously generates events during normal operation.
- Security solutions analyze these events and generate alerts when suspicious behavior is detected.
- Alerts become incidents only after analysts confirm malicious activity.
- False Positives are benign activities incorrectly flagged as malicious, while True Positives represent genuine threats.
- Incident severity helps organizations prioritize response efforts based on business impact.
- Common incident categories include malware infections, security breaches, data leaks, insider attacks, and denial of service attacks.
- Effective Incident Response begins with accurate detection, investigation, and classification of security events.

# Incident Response Frameworks

Handling security incidents without a structured process can quickly become chaotic, especially in large organizations where multiple incidents may occur simultaneously. To ensure consistency, efficiency, and proper coordination, organizations follow **Incident Response Frameworks**.

These frameworks provide standardized guidance on how to prepare for, detect, contain, eradicate, recover from, and learn from cybersecurity incidents.

The two most widely adopted frameworks are:

- **SANS Incident Response Framework**
- **NIST Incident Response Framework**

Although they differ slightly in structure, both frameworks share the same objective: minimizing the impact of security incidents while restoring business operations as quickly and safely as possible.

---

# SANS Incident Response Framework (PICERL)

The **SANS Institute** defines a six-phase Incident Response lifecycle commonly remembered using the acronym **PICERL**.

```text
Preparation
      │
      ▼
Identification
      │
      ▼
Containment
      │
      ▼
Eradication
      │
      ▼
Recovery
      │
      ▼
Lessons Learned
```

Each phase builds upon the previous one to ensure incidents are handled methodically.

---

## Phase 1 — Preparation

Preparation occurs **before any incident takes place**.

The objective is to ensure that the organization has the people, processes, and technologies required to respond effectively when an incident occurs.

Typical preparation activities include:

- Building an Incident Response Team (IRT)
- Developing an Incident Response Plan (IRP)
- Deploying SIEM and EDR solutions
- Implementing backup strategies
- Conducting security awareness training
- Creating incident playbooks
- Performing tabletop exercises

Example:

Employees receive phishing awareness training to reduce the likelihood of opening malicious email attachments.

---

## Phase 2 — Identification

The Identification phase focuses on determining whether suspicious activity represents a legitimate security incident.

Security teams analyze alerts generated by monitoring tools and investigate abnormal behavior.

Typical indicators include:

- Malware detections
- Unusual outbound traffic
- Multiple failed login attempts
- Suspicious PowerShell execution
- Unauthorized account activity

Example:

A security analyst observes unusually large outbound network traffic and confirms that malware executed after a user opened a phishing attachment.

---

## Phase 3 — Containment

Once an incident has been confirmed, the priority becomes preventing further damage.

Containment limits the attack's impact while allowing investigators to continue collecting evidence.

Common containment actions include:

- Isolating compromised hosts
- Disabling compromised user accounts
- Blocking malicious IP addresses
- Blocking malicious domains
- Quarantining infected files

Example:

An infected workstation is isolated from the corporate network to prevent malware from spreading to additional systems.

---

## Phase 4 — Eradication

After containment, the threat must be completely removed from the environment.

Eradication focuses on eliminating both the malware and its underlying cause.

Typical activities include:

- Removing malware
- Deleting persistence mechanisms
- Resetting compromised credentials
- Patching exploited vulnerabilities
- Removing malicious scheduled tasks or services

Example:

A full malware scan identifies and removes all malicious files from the infected endpoint.

---

## Phase 5 — Recovery

Recovery restores affected systems to normal business operation.

Recovered systems should be validated before reconnecting them to production environments.

Recovery activities may include:

- Restoring systems from backups
- Rebuilding compromised machines
- Verifying system integrity
- Monitoring recovered systems
- Returning systems to production

Example:

The compromised workstation is rebuilt and business data is restored from a verified backup.

---

## Phase 6 — Lessons Learned

Lessons Learned is the final phase of the Incident Response lifecycle.

Rather than ending the investigation, organizations analyze the incident to improve future response capabilities.

Typical activities include:

- Root cause analysis
- Updating detection rules
- Improving playbooks
- Reviewing response timelines
- Enhancing employee awareness training
- Documenting recommendations

Example:

Following a phishing incident, the organization updates its email filtering policies and provides additional phishing awareness training to employees.

---

# NIST Incident Response Framework

The **National Institute of Standards and Technology (NIST)** provides a simplified Incident Response lifecycle consisting of four phases.

```text
Preparation
      │
      ▼
Detection & Analysis
      │
      ▼
Containment, Eradication & Recovery
      │
      ▼
Post-Incident Activity
```

Rather than separating each operational stage, NIST combines several related activities into broader categories.

---

## Phase 1 — Preparation

Equivalent to the SANS Preparation phase.

Organizations establish policies, procedures, technologies, and trained personnel before incidents occur.

---

## Phase 2 — Detection and Analysis

This phase combines incident identification with detailed investigation.

Analysts determine:

- Whether an incident has occurred
- How the attack happened
- Which systems are affected
- The scope of the compromise
- The incident severity

---

## Phase 3 — Containment, Eradication, and Recovery

NIST groups operational response activities into one phase.

Organizations:

- Limit the spread of the attack
- Remove the threat
- Restore affected services
- Validate recovered systems

---

## Phase 4 — Post-Incident Activity

Equivalent to the **Lessons Learned** phase in the SANS framework.

Organizations perform:

- Incident documentation
- Root cause analysis
- Detection improvements
- Policy updates
- Security awareness improvements

---

# SANS vs NIST Comparison

| SANS | NIST |
|------|------|
| Preparation | Preparation |
| Identification | Detection & Analysis |
| Containment | Containment, Eradication & Recovery |
| Eradication | Containment, Eradication & Recovery |
| Recovery | Containment, Eradication & Recovery |
| Lessons Learned | Post-Incident Activity |

Although the terminology differs, both frameworks follow the same overall objective:

1. Prepare for incidents.
2. Detect and investigate malicious activity.
3. Contain and eliminate threats.
4. Restore normal operations.
5. Learn from every incident.

---

# Incident Response Plan (IRP)

Following a framework alone is not sufficient.

Organizations require a formal document describing exactly how incidents should be handled.

This document is known as the **Incident Response Plan (IRP)**.

An IRP ensures every responder understands:

- What actions to perform
- Who is responsible
- How incidents are escalated
- How communication is managed

The Incident Response Plan is typically approved by senior management and serves as the organization's official response procedure.

---

# Core Components of an Incident Response Plan

## Roles and Responsibilities

Defines who performs each task during an incident.

Common roles include:

- SOC Analyst
- Incident Responder
- Digital Forensics Analyst
- System Administrator
- Security Manager
- Legal Team
- Human Resources
- Public Relations

---

## Incident Response Methodology

Describes the organization's standardized approach for handling incidents.

This typically references established frameworks such as SANS or NIST.

---

## Communication Plan

Defines how information is communicated during an incident.

Stakeholders may include:

- Executive management
- IT teams
- Legal department
- Customers
- Third-party vendors
- Law enforcement agencies

Clear communication helps minimize confusion during high-pressure situations.

---

## Escalation Path

Not every incident requires the same response team.

The escalation path determines how incidents move through different support levels.

Example:

```text
SOC Tier 1
      │
      ▼
SOC Tier 2
      │
      ▼
SOC Tier 3
      │
      ▼
Incident Response Team
      │
      ▼
Management
```

Critical incidents are escalated more quickly than lower-priority events.

# Incident Response Technologies

Modern organizations generate millions of security events every day. Manually reviewing these events is impossible, making security technologies essential for detecting, investigating, and responding to cyber threats.

This room introduces three of the most common security solutions used throughout the Incident Response lifecycle:

- Security Information and Event Management (SIEM)
- Antivirus (AV)
- Endpoint Detection and Response (EDR)

Each technology plays a different role, and together they provide comprehensive visibility across an organization's environment.

---

# Security Information and Event Management (SIEM)

## What is SIEM?

A **Security Information and Event Management (SIEM)** platform collects logs from multiple systems, centralizes them, and correlates events to identify suspicious activity.

Instead of analysts reviewing logs from individual devices, the SIEM aggregates everything into a single location for investigation.

---

## Why SIEM is Needed

A modern enterprise may contain:

- Windows servers
- Linux servers
- Firewalls
- Routers
- VPN gateways
- Cloud services
- Endpoint devices
- Web applications

Each system generates thousands of logs every hour.

Without SIEM:

```text
Windows Logs

Linux Logs

Firewall Logs

VPN Logs

Cloud Logs

Web Server Logs
```

Analysts would need to investigate each source individually.

With SIEM:

```text
Windows
      │
Linux
      │
Firewall
      │
VPN
      │
Cloud
      │
Endpoints
      ▼

      SIEM
        │
        ▼
Security Analysts
```

Everything is centralized into a single platform.

---

## Core Functions of SIEM

### Log Collection

SIEM continuously collects logs from multiple devices and services.

Examples include:

- Windows Event Logs
- Linux Syslog
- Firewall logs
- DNS logs
- Authentication logs
- Web server logs
- Cloud logs

---

### Log Normalization

Different systems record information using different formats.

SIEM normalizes these logs into a standardized format, making searches and correlation much easier.

---

### Event Correlation

Correlation is one of SIEM's most powerful capabilities.

Instead of analyzing individual events, SIEM connects related activities together.

Example:

```text
09:00

100 Failed Logins

↓

09:02

Successful Login

↓

09:04

PowerShell Execution

↓

09:05

Outbound Network Connection

↓

Generate Alert
```

Each individual event may appear harmless, but together they indicate a potential compromise.

---

## Common SIEM Platforms

Examples include:

- Splunk Enterprise Security
- Microsoft Sentinel
- IBM QRadar
- Elastic Security
- Wazuh
- ArcSight

---

## Advantages

- Centralized log management
- Powerful event correlation
- Threat hunting capabilities
- Real-time alerting
- Compliance reporting

---

## Limitations

SIEM primarily detects suspicious activity.

Most SIEM platforms cannot directly stop attacks without integration with other security technologies.

# Antivirus (AV)

## What is Antivirus?

Antivirus software is designed to detect, block, and remove malicious software from a system.

It provides the first layer of endpoint protection against known threats.

---

## How Antivirus Works

Traditional antivirus solutions compare files against a database of known malware signatures.

```text
File Created
      │
      ▼
Signature Scan
      │
      ▼
Known Malware?
      │
 ┌────┴────┐
 │         │
Yes        No
 │          │
 ▼          ▼
Quarantine Continue
```

Modern antivirus solutions may also use heuristic analysis and machine learning to identify suspicious behavior.

---

## Detection Methods

### Signature-Based Detection

Compares file hashes and signatures against a malware database.

Effective against:

- Known malware
- Previously identified threats

---

### Heuristic Detection

Looks for suspicious behavior instead of exact signatures.

Examples include:

- Self-modifying code
- Obfuscated executables
- Suspicious API usage

---

## Advantages

- Fast malware detection
- Lightweight protection
- Effective against known threats
- Automatic quarantine

---

## Limitations

Traditional antivirus solutions may struggle against:

- Zero-day attacks
- Fileless malware
- Living-off-the-Land (LotL) attacks
- Advanced Persistent Threats (APTs)

---

# Endpoint Detection and Response (EDR)

## What is EDR?

**Endpoint Detection and Response (EDR)** provides continuous monitoring of endpoint devices such as:

- Workstations
- Laptops
- Servers
- Virtual machines

Unlike traditional antivirus software, EDR focuses on behavioral analysis rather than only identifying malicious files.

---

## How EDR Works

EDR continuously monitors endpoint activity, including:

- Process creation
- Parent-child process relationships
- Network connections
- Registry modifications
- File activity
- Command-line arguments
- User logins
- Memory behavior

This provides significantly greater visibility into attacker activity.

---

## Example

Suppose Microsoft Word unexpectedly launches PowerShell.

```text
Word.exe
      │
      ▼
PowerShell.exe
      │
      ▼
Downloads Payload
      │
      ▼
Suspicious DNS Request
```

Although no malware signature exists, this behavior is highly suspicious.

An EDR platform can detect this activity using behavioral analysis.

---

## Automated Response

One of the biggest advantages of EDR is its ability to automatically respond to threats.

Common response actions include:

- Isolating infected hosts
- Killing malicious processes
- Quarantining malicious files
- Collecting forensic artifacts
- Alerting SOC analysts

Example:

```text
Malware Detected
      │
      ▼
Kill Process
      │
      ▼
Isolate Host
      │
      ▼
Quarantine File
      │
      ▼
Notify Security Team
```

---

## Common EDR Platforms

Examples include:

- Microsoft Defender for Endpoint
- CrowdStrike Falcon
- SentinelOne
- VMware Carbon Black
- Trellix Endpoint Security

# Incident Response Playbooks

After an incident has been detected, analysts must follow predefined procedures to ensure a consistent response.

These high-level procedures are known as **Playbooks**.

A playbook defines **what actions should be taken** for a specific type of incident.

Example:

## Phishing Email Playbook

```text
Phishing Alert
      │
      ▼
Notify Stakeholders
      │
      ▼
Analyze Email Headers
      │
      ▼
Inspect Attachments
      │
      ▼
Identify Affected Users
      │
      ▼
Isolate Infected Systems
      │
      ▼
Block Sender
```

Every phishing incident follows a similar investigation process, allowing analysts to respond consistently.

---

# Runbooks

A **Runbook** provides detailed technical instructions for completing a specific task within a playbook.

Where a playbook defines **what** should be done, a runbook explains **how** to perform each action.

Example:

## Host Isolation Runbook

```text
Open EDR Console
      │
      ▼
Search Device Name
      │
      ▼
Select Endpoint
      │
      ▼
Click "Isolate Device"
      │
      ▼
Confirm Action
      │
      ▼
Verify Isolation Status
```

Runbooks reduce human error and ensure technical procedures are executed consistently.

---

# Playbooks vs Runbooks

| Playbook | Runbook |
|-----------|----------|
| High-level incident response guide | Detailed technical execution guide |
| Describes what should be done | Describes how each task is performed |
| Covers an entire incident type | Focuses on a specific operational task |
| Used throughout the response process | Used during individual response actions |
| Example: Phishing Response | Example: Host Isolation Procedure |

- Automate repetitive tasks
- Improve collaboration across security teams

Together, these technologies and procedures form the operational foundation of modern Incident Response.

---

# Key Takeaways

- SIEM centralizes, normalizes, and correlates logs from multiple systems to identify suspicious activity.
- Antivirus protects endpoints by detecting and removing known malware using signatures and heuristic analysis.
- EDR provides continuous endpoint monitoring, behavioral detection, and automated response capabilities.
- SIEM, Antivirus, and EDR complement each other and are commonly deployed together in enterprise environments.
- Playbooks define the high-level response process for specific incident types.
- Runbooks provide detailed technical procedures for executing individual response tasks within a playbook.
- Standardized response procedures improve consistency, reduce response time, and strengthen an organization's overall security posture.

# Troubleshooting & Lessons Learned

During this room, no technical issues were encountered. However, several conceptual topics required careful attention due to their similar terminology.

## Distinguishing Events, Alerts, and Incidents

One of the easiest mistakes for beginners is assuming that every alert is automatically an incident.

Correct understanding:

```text
Event
   │
   ▼
Alert
   │
   ▼
Security Investigation
   │
   ├────────────► False Positive
   │
   ▼
True Positive
   │
   ▼
Incident
```

Only **True Positive** alerts become security incidents.

---

## Downloaded vs Executed Malware

Another important lesson was understanding that downloading a malicious file does not necessarily mean a system is compromised.

Example:

```text
Downloaded
```

↓

The malicious file exists on disk.

↓

The endpoint may simply require file quarantine.

Whereas:

```text
Executed
```

↓

The malware becomes active.

↓

The endpoint is compromised and requires containment.

This distinction determined the different response actions performed during the lab.

---

## Playbook vs Runbook

This room introduces both concepts, which are commonly confused.

| Playbook | Runbook |
|-----------|----------|
| High-level response guide | Detailed technical procedure |
| Covers an entire incident type | Covers a specific operational task |
| Defines **what** should be done | Defines **how** to perform each step |

For example:

**Playbook**

```text
Phishing Incident

↓

Investigate

↓

Contain

↓

Recover
```

**Runbook**

```text
Host Isolation

↓

Open EDR Console

↓

Select Device

↓

Click Isolate
```
