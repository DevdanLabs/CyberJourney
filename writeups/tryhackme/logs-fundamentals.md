Logs are one of the most valuable sources of information in cybersecurity. Every action performed by users, applications, operating systems, and network devices leaves digital traces known as **logs**. Security professionals rely on these logs to monitor systems, investigate incidents, troubleshoot problems, and reconstruct attack timelines.

Through two practical investigations, I identified suspicious user account activities using Windows Security Event Logs and analyzed web server access logs to determine HTTP requests, timestamps, client IP addresses, and requested resources. These exercises demonstrate how log analysis forms the foundation of Security Operations Center (SOC) investigations, Digital Forensics, Incident Response (DFIR), and Threat Hunting.

# Windows Event Logs Overview

Windows records system and security events using **Windows Event Logs**.

The primary Windows log categories include:

| Log | Purpose |
|------|----------|
| **Application** | Records events generated by installed applications. |
| **System** | Records operating system events, hardware activities, drivers, and services. |
| **Security** | Records authentication, authorization, account management, and security-related events. |

Windows provides a built-in graphical utility called **Event Viewer** that allows administrators and security analysts to browse, filter, and investigate these logs efficiently.

Each event contains detailed information such as:

- Event ID
- Timestamp
- Log Name
- Event Description
- User Information
- Source

Event IDs are particularly useful because each ID represents a specific type of activity, allowing analysts to quickly filter and investigate relevant events.

# Web Server Access Logs Overview

Whenever a client communicates with a web server, the request is recorded inside the web server's access log.

Apache Access Logs typically contain information such as:

- Client IP Address
- Timestamp
- HTTP Method
- Requested URL
- HTTP Version
- Response Status Code
- User-Agent

Example:

```text
172.16.0.1 - - [06/Jun/2024:13:58:44] "GET /contact HTTP/1.1" 200 "-" "Mozilla/5.0 ..."
```

Each field provides valuable information during investigations:

| Field | Description |
|--------|-------------|
| IP Address | Identifies the client making the request. |
| Timestamp | Shows exactly when the request occurred. |
| HTTP Method | Indicates the action requested (GET, POST, etc.). |
| URL | Specifies the requested resource. |
| Status Code | Indicates the server's response. |
| User-Agent | Provides browser and operating system information. |

Because every HTTP request is recorded, web server access logs are one of the primary sources of evidence during web application security investigations.

# Log Analysis Fundamentals

Logs often contain thousands or even millions of events, making manual inspection nearly impossible. **Log analysis** is the process of examining logs to extract meaningful information, identify suspicious activities, troubleshoot issues, and reconstruct security incidents.

Rather than reading every log entry individually, security analysts search for patterns, filter specific events, correlate multiple data sources, and build timelines of system activities.

Log analysis is one of the core responsibilities of Security Operations Center (SOC) analysts, Incident Responders, Digital Forensics investigators, and Threat Hunters.

---

# Why Log Analysis Matters

Logs provide evidence for nearly every activity performed within an information system.

Without logs, investigators cannot accurately determine:

- Who performed an action
- When the activity occurred
- Which systems were affected
- How an attacker gained access
- What actions were performed after compromise
- Whether sensitive data was accessed or exfiltrated

Logs serve as the primary source of truth during investigations.

---

# Filtering Logs Using Event IDs

Instead of manually reviewing every event, Event Viewer allows analysts to filter logs using specific Event IDs.

Example:

```
Event ID:
4624
```

This filter immediately displays every successful logon event.

Similarly:

```
4720
```

shows all newly created user accounts.

Filtering dramatically reduces the number of events that investigators need to examine.

# Apache Web Access Log Structure

Apache Web Server records every HTTP request made to a website.

A typical log entry looks like this:

```text
172.16.0.1 - - [06/Jun/2024:13:58:44] "GET /products HTTP/1.1" 404 "-" "Mozilla/5.0 ..."
```

Each section of the log has a specific meaning.

| Field | Example | Description |
|--------|---------|-------------|
| Client IP | 172.16.0.1 | Source IP address of the client |
| Timestamp | 06/Jun/2024:13:58:44 | Date and time of the request |
| HTTP Method | GET | Action requested by the client |
| URL | /products | Requested resource |
| HTTP Version | HTTP/1.1 | HTTP protocol version |
| Status Code | 404 | Server response code |
| User-Agent | Mozilla/... | Browser and operating system information |

Understanding this structure allows analysts to reconstruct web activity from raw logs.

---

# HTTP Request Methods

HTTP methods describe the action requested by the client.

## GET

Retrieves resources from the web server.

Example:

```http
GET /contact HTTP/1.1
```

Typical use cases:

- Visiting a webpage
- Loading images
- Downloading files

GET requests generally do not modify server-side data.

---

## POST

Sends data to the web server.

Example:

```http
POST /login HTTP/1.1
```

Typical use cases:

- User authentication
- Form submissions
- File uploads
- Sending API requests

POST requests often modify server-side data.

---

# Common HTTP Status Codes

Web servers respond to requests using HTTP status codes.

| Status Code | Meaning |
|-------------|---------|
| **200** | Request completed successfully |
| **301** | Resource permanently redirected |
| **302** | Temporary redirect |
| **400** | Bad request |
| **401** | Unauthorized |
| **403** | Forbidden |
| **404** | Resource not found |
| **500** | Internal server error |

Status codes help analysts determine whether requests succeeded or failed.

# Manual vs Automated Log Analysis

Manual log analysis is useful for understanding how logs are structured and for investigating small datasets.

However, enterprise environments generate millions of log entries every day, making manual analysis impractical.

Organizations therefore use Security Information and Event Management (SIEM) platforms such as:

- Splunk
- Microsoft Sentinel
- Elastic Stack (ELK)
- IBM QRadar

These platforms automatically collect, index, correlate, search, and visualize logs from multiple systems, enabling analysts to detect suspicious activities much faster.

Understanding manual log analysis is an essential prerequisite before learning SIEM platforms because it builds the foundation for interpreting raw log data.

# Understanding Event ID 4720

Whenever a new local or domain account is created, Windows generates Event ID **4720**.

The event records:

- Who created the account
- The newly created username
- Security Identifier (SID)
- Time of creation

This event is commonly investigated because attackers often create new administrator accounts to maintain persistence after gaining privileged access.

# Understanding Event ID 4722

Creating an account does not always mean the account is immediately usable.

Windows records Event ID **4722** whenever an account is enabled.

This distinction is important because attackers may:

```

```

Knowing exactly when an account became active helps investigators build a more accurate attack timeline.

# Attack Timeline Reconstruction

Using multiple Event IDs, we can reconstruct the attacker's activity.

```text

        │
        ▼

Create New User
        │
        ▼
User Account
"hacked"
        │
        ▼
Event ID 4722
Account Enabled
        │
        ▼
Event ID 4724
Password Reset
        │
        ▼
Potential Future Logon
(Event ID 4624)
```

Instead of examining individual events in isolation, investigators combine multiple Event IDs to reconstruct the attack timeline. This process is one of the fundamental techniques used in Digital Forensics and Incident Response (DFIR), allowing analysts to understand not only **what happened**, but also **when it happened** and **who performed each action**.

| Successful Logon | 4624 |
| Failed Logon | 4625 |
| User Account Creation | 4720 |
| User Account Enabled | 4722 |
| Password Reset | 4724 |
| User Account Disabled | 4725 |
| User Account Deleted | 4726 |

If an attacker compromises an administrator account and creates a new user for persistence, Windows automatically records these events.

Example attack sequence:

```text
Initial Compromise
        │
        ▼
Privilege Escalation
        │
        ▼
Create User (4720)
        │
        ▼
Enable User (4722)
        │
        ▼
Reset Password (4724)
        │
        ▼
Successful Login (4624)
```

For defenders, these events provide valuable evidence when reconstructing an attack timeline.

## Web Server Access Logs

Every interaction with a web application is typically recorded in the web server's access log.

Examples of logged activities include:

- Browsing web pages
- Login attempts
- File uploads
- Form submissions
- API requests
- Download requests

Even simple reconnaissance leaves evidence.

Example:

```http
GET /robots.txt
```

```http
GET /admin
```

```http
GET /.git
```

Similarly, exploitation attempts also generate log entries.

Examples:

```http
GET /?id=1'
```

(SQL Injection attempt)

```http
GET /../../etc/passwd
```

(Local File Inclusion attempt)

```http
POST /login
```

(Brute-force or credential stuffing attempt)

Because every request is recorded, web access logs are often the first place investigators examine after a web application attack.

# Common Misconfigurations

Several common logging mistakes reduce an organization's ability to detect attacks.

Examples include:

- Logging disabled on critical systems.
- Logs stored only locally.
- Short log retention periods.
- Unsynchronized system clocks.
- Excessive permissions allowing attackers to modify logs.
- Failure to centralize logs from multiple systems.
- Lack of regular log monitoring.

These issues significantly hinder incident response and forensic investigations.

# Troubleshooting

During manual log analysis, several challenges may arise.

| Problem | Possible Cause | Solution |
|----------|---------------|----------|
| No matching results from `grep` | Incorrect search pattern | Verify spelling, capitalization, and search terms. |
| Missing Windows events | Incorrect Event ID filter | Confirm the correct Event ID is being used. |
| Unable to locate a specific request | Searching the wrong log file | Verify the correct access log is being analyzed. |
| Excessive log output | Broad search criteria | Apply additional filters using IP addresses, URLs, or HTTP methods. |
| Difficult timeline reconstruction | Mixed log sources | Sort events chronologically and correlate timestamps across logs. |

# Key Takeaways

This room introduced the fundamentals of log analysis and demonstrated why logs are one of the most valuable sources of evidence in cybersecurity. Every action performed by users, applications, operating systems, and network devices leaves digital footprints that can be collected, analyzed, and correlated during security investigations.

One of the most important lessons learned is that different types of logs serve different purposes. Rather than storing every event in a single location, operating systems and applications organize logs into categories such as System, Security, Application, Audit, Network, and Access logs. Understanding where specific events are recorded allows investigators to quickly locate relevant evidence.

The practical exercises also demonstrated that effective investigations rely on filtering and correlation rather than manually reading every log entry. Whether using Windows Event Viewer to search for specific Event IDs or Linux command-line tools to filter Apache access logs, analysts focus only on the events relevant to the investigation.

Finally, this room reinforced that log analysis forms the foundation of many cybersecurity disciplines, including Security Operations (SOC), Digital Forensics and Incident Response (DFIR), Threat Hunting, Security Engineering, and Penetration Testing.

# Commands Used
